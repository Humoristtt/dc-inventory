# Разработка

Документ описывает локальную разработку и проверку изменений. Production VM не является dev-средой.

## 1. Toolchain

Backend:

- Python 3.12;
- FastAPI;
- SQLAlchemy 2 async;
- asyncpg;
- Alembic;
- PostgreSQL 18.

Frontend:

- Node.js 24+;
- React 19;
- TypeScript 6;
- Vite 8;
- Vitest;
- Playwright.

Runtime:

- Docker + Docker Compose plugin.

Версии Python dependencies зафиксированы в `backend/requirements*.lock`. Frontend dependencies — `frontend/package-lock.json`.

## 2. Первичная установка

Backend:

```bash
cd backend
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install --require-hashes -r requirements-dev.lock
```

Frontend:

```bash
cd frontend
npm ci
npx playwright install chromium webkit
```

Не использовать `npm audit fix --force` или массовое обновление Python dependencies без отдельного анализа.

## 3. Локальная конфигурация

`.env.example` — перечень допустимых variables и placeholders.

Реальный `.env` не коммитится.

Для проверки ключей:

```bash
python3 ops/validate_env_file.py .env
```

Production-подобная проверка placeholders/DB secret encoding:

```bash
python3 ops/validate_env_file.py --production .env
```

## 4. Dev Compose

`compose.dev.yaml` публикует только loopback ports для локальной работы.

Перед запуском нужны как минимум PostgreSQL variables и `DATABASE_URL`.

Пример:

```bash
docker compose --env-file .env -f compose.dev.yaml up -d --build
```

Остановить:

```bash
docker compose --env-file .env -f compose.dev.yaml down
```

Dev volume не использовать как production data.

## 5. Миграции

Из `backend/`:

```bash
alembic heads
alembic upgrade head
alembic current
alembic check
```

Правила:

- должен быть один head;
- старые migration files не переписываются ради новой функции;
- autogenerated migration читается вручную;
- historical migration не импортирует изменяемые runtime constants;
- destructive downgrade проверяется отдельно;
- mutation test выполняется только на disposable DB.

Source head определяется самим Alembic graph, а не документацией.

## 6. Backend checks

Быстрые static checks:

```bash
cd backend
ruff check app tests migrations
mypy app tests migrations/env.py migrations/versions
```

Focused test:

```bash
pytest -q path/to/test_file.py
```

Полный backend gate на disposable PostgreSQL:

```bash
RUN_POSTGRES_INTEGRATION=1 pytest -q
```

DB-related change должен также проходить migration from zero to head и соответствующие real-PostgreSQL regressions.

## 7. Frontend checks

```bash
cd frontend
npm run lint
npm run typecheck
npm test
npm run build
```

`npm run build` включает:

1. design-system architecture contract;
2. TypeScript build;
3. Vite production build;
4. bundle-size/lazy-route contract.

Browser scenarios:

```bash
npm run test:e2e
```

Файлы:

- `frontend/e2e/warehouse-v2.spec.ts`;
- `frontend/e2e/procurement.spec.ts`.

## 8. Full-stack acceptance

Локальный isolated full-stack entrypoint:

```bash
cd frontend
npm run test:e2e:fullstack:local
```

Он должен использовать disposable PostgreSQL/runtime и не подключаться к production.

GitHub runtime job дополнительно запускает `frontend/e2e/fullstack.spec.ts` против production-shaped Compose и после browser flow проверяет фактические DB side effects.

## 9. Database invariants

Если change затрагивает migrations, Catalog identity, Warehouse, Procurement или DB grants, проверяются:

- fresh upgrade;
- negative DB invariant tests;
- readiness;
- runtime least-privilege matrix;
- migration downgrade там, где он поддерживается;
- reconciliation для Warehouse projection.

Нельзя закрывать database finding только unit-test с mocked DB.

## 10. Query scalability

Для Catalog/Procurement/Inventory query refactor не считать число Python loops показателем производительности.

Использовать существующие real-PostgreSQL query-count/performance contracts. При изменении semantics сначала сохранить correctness test, затем оптимизировать plan.

## 11. Безопасность test data

Запрещено:

- включать `REAL_INVENTORY_MUTATIONS_ENABLED=true` против общей/production DB ради теста;
- использовать production bot/email credentials;
- загружать production dump в незащищённую среду;
- коммитить workbook с реальным inventory.

Synthetic fixtures должны быть явно synthetic.

## 12. Документация

При изменении domain semantics обновляется ровно соответствующий current-state документ.

Проверка:

```bash
python3 ops/tests/test_docs_structure.py
python3 ops/tests/test_docs_freshness.py
python3 ops/tests/test_repository_data_policy.py
python3 ops/tests/test_notification_delivery_contract.py
python3 ops/tests/test_recovery_runbook_contract.py
```

Не добавлять отдельный historical journal для каждого change-set.

## 13. Порядок разработки

Рекомендуемый цикл:

```text
прочитать affected code/contract
→ воспроизвести defect или зафиксировать invariant
→ минимальный change
→ focused test
→ полный затронутый gate один раз
→ CI
```

Не повторять весь suite после каждой строки изменения.

## 14. Production boundary

Локальный PASS не означает production acceptance.

Из development flow запрещено автоматически:

- менять production env;
- запускать production migrations;
- переключать ingress;
- менять Telegram webhook;
- включать email;
- выполнять restore/cutover.

Для этого используется [DEPLOYMENT.md](DEPLOYMENT.md) и отдельное разрешение.
