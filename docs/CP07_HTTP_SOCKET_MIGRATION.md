# CP-07 HTTP: подготовка доверенного Unix-origin

Статус: локальная реализация. Production не переключён.

## Причина

На production cloudflared подключается к http://localhost:8080.
Nginx видит источник Docker/host, а не IP Cloudflare.

Доверие ко всем CF-Connecting-IP на TCP позволяет локальным
процессам с доступом к origin подменять адрес клиента.

Доверие только к публичным диапазонам Cloudflare также
неподходящее решение: cloudflared подключается локально,
и все пользователи могут попасть в один rate-limit bucket.

## Новая схема

TCP :8080:
- не доверяет CF-Connecting-IP;
- rate limit использует адрес TCP-источника;
- не доверяет входящему X-Forwarded-Proto.

Unix /run/dc-inventory/ingress.sock:
- предназначен для cloudflared;
- real_ip_header CF-Connecting-IP;
- set_real_ip_from unix:;
- rate limit использует адрес клиента после real_ip;
- upstream получает нормализованные IP и HTTPS.

Cloudflare origin после переключения:
unix:/ABSOLUTE/HOST/PATH/ingress.sock

## Условия переключения production

1. Выяснить фактического пользователя systemd-сервиса cloudflared.
2. Проверить UID/GID nginx в закреплённом Docker-образе.
3. Создать отдельный host-каталог с ограниченными правами.
4. Разрешить доступ к каталогу только nginx и cloudflared
   (либо использовать root для cloudflared, если это подтверждено).
5. Проверить доступ к сокету от пользователя cloudflared.
6. Убедиться, что Unix-origin доступен, до изменения маршрута.
7. Переключить Cloudflare origin согласованно с выпуском web-образа.
8. Проверить health, вход, раздельные rate-limit buckets и логи.

Нельзя просто развернуть новый web-образ и оставить production
Tunnel на TCP:8080: реальные клиенты будут делить один лимит.

## Откат

Откат требует согласованного возврата и маршрута Tunnel,
и предыдущего web-образа. Возвращать только TCP-маршрут
без предыдущего web-образа нельзя.

Тесты на Mac проверяют поведение Nginx в Docker.
Они не подтверждают host-права production VM или
доступ systemd cloudflared к Unix-сокету.

## Обязательные права production-каталога

Защитная граница — права каталога, а не самого Unix-сокета.

Перед запуском web необходимо подготовить host-каталог:

- владелец: фактический UID процесса nginx в контейнере;
- группа: отдельная группа, разрешённая cloudflared;
- режим каталога: 0750;
- посторонние пользователи не должны входить в разрешённую группу.

Проверить UID/GID nginx и пользователя cloudflared непосредственно
на production VM. Значения из локального теста не переносить автоматически.

Каталог должен существовать до запуска Compose. Не разрешать
автоматическое создание каталога с правами по умолчанию.

Nginx может создавать сам сокет с режимом 0666. При закрытом
родительском каталоге посторонние пользователи не могут до него
добраться.

Dockerfile устанавливает 0750 только для каталога внутри образа.
Bind mount скрывает этот каталог: на production должны быть
правильно настроены права именно host-каталога.

При старте и после перезапуска проверить:

- владелец и режим host-каталога;
- доступ к сокету от пользователя cloudflared;
- отказ в подключении от постороннего пользователя.

Без этих проверок migration запрещена.

## Результаты локальных проверок — 19.09.2026

Сборка Docker-образа и `nginx -t` — PASS.

Изолированные runtime-тесты:

- TCP, десять запросов с изменяемым `CF-Connecting-IP`: шесть HTTP 200, затем четыре HTTP 429.
- TCP передаёт backend адрес непосредственного источника и схему `http`, игнорируя поддельные клиентские заголовки.
- Unix, один клиент: шесть HTTP 200, затем четыре HTTP 429.
- Unix передаёт backend адрес клиента из доверенного заголовка и схему `https`.
- Второй клиент через Unix получает HTTP 200 и отдельный лимит.

Проверка прав:

- без ограничения каталога сокет имел режим `0666`, посторонний пользователь мог подключиться — FAIL;
- каталог `0750`, владелец `101`, тестовая группа `201`;
- пользователь `65534:65534`: подключение запрещено — PASS;
- пользователь `65533:201`: подключение разрешено — PASS.

При первоначальном тесте Docker-том изменил группу каталога
с `201` на `101` во время инициализации. Повторная установка прав
после запуска Nginx дала ожидаемый результат. Для production
используется bind mount: права необходимо выставить и проверить
на host-каталоге до переключения Tunnel.

Все указанные проверки выполнены локально на MacBook в Docker.
Проверка production UID/GID, системного пользователя cloudflared,
host-каталога и фактического Tunnel-origin ещё не выполнена.

Статус: локальная реализация проверена; production migration OPEN.
