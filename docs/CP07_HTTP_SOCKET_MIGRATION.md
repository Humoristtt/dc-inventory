# CP-07 — переключение Cloudflare Tunnel на доверенный Unix-вход Nginx

**Состояние на 25.09.2026: production migration — CLOSED / PASS.** Release `593ddec0c9100b0df2eafe4f324c7bb600d75cba` развернут и принят. Пользовательский ingress переведён на direct HTTPS через host Nginx и Unix socket; Cloudflare Tunnel больше не обслуживает пользовательский `app.spik-inventory.ru` и используется только для входящего Telegram webhook. Разделы 1–7 ниже сохранены как исторический план и evidence перехода; фактическая конечная схема описана в разделе 8. Общий порядок выпуска и восстановления: [DEPLOYMENT.md](DEPLOYMENT.md) и [RECOVERY_RUNBOOK.md](RECOVERY_RUNBOOK.md).

## 1. Какой дефект устраняем

По последней документированной production-конфигурации `cloudflared` обращается к `http://localhost:8080`. На этом стыке Nginx видит адрес непосредственного TCP-соединения, а не публичный адрес пользователя. Если безусловно доверять входящему `CF-Connecting-IP` на TCP, локальный процесс может подставить произвольный IP. Если вообще не доверять этому заголовку, все пользователи Tunnel могут попасть в один rate-limit bucket. Доверие к публичным диапазонам Cloudflare не решает проблему: непосредственный источник соединения — локальный `cloudflared`, а не edge-сервер Cloudflare.

Поэтому в исходниках разделены **два ingress**, которым нельзя назначать одинаковые правила доверия. Никакой из них не должен становиться общедоступным без отдельного решения.

## 2. Реализованные входы и границы доверия

Конфигурация: `frontend/nginx.conf` и `frontend/nginx-server.inc`.

| Вход | Назначение | Доверие к заголовкам | Лимит и upstream |
|---|---|---|---|
| TCP `:8080` | Локальный недоверенный вход | Не принимает заявленный клиентом IP как реальный; `$forwarded_proto` берётся из `$scheme` | Ключ ограничения запросов — адрес TCP-источника. |
| Unix `/run/dc-inventory/ingress.sock` | Доверенный вход только от `cloudflared` | `set_real_ip_from unix:` и `real_ip_header CF-Connecting-IP`; схема upstream принудительно `https` | `$remote_addr` после обработки доверенного заголовка используется для разделения клиентов. |

Оба входа подключают общий `server-common.inc`: различается **только** граница доверия и способ определения адреса/схемы. В текущем Nginx общий API ограничивается 30 запросами/с на ключ, чувствительные запросы авторизации/доступа — 10 запросами/мин, webhook — отдельно 50 запросами/с; превышение возвращает HTTP 429. Не описываем эти значения как защиту от всех вариантов DoS.

Unix-сокет может создаваться с режимом `0666`. В этой схеме реальной границей доступа служит **родительский каталог с режимом `0750`**, владелец и группа которого проверены для конкретных процессов. Закрытого socket-файла недостаточно, если любой локальный пользователь может пройти через каталог. Внутренний каталог из Docker image перекрывается bind mount, поэтому его исходные права не подтверждают права host-каталога.

## 3. Что нужно установить до переключения

1. Зафиксировать approved SHA, точные image IDs/revisions, текущий Tunnel origin, вариант отката, свежую проверенную резервную копию и отдельное разрешение на CP-16/CP-07.
2. Проверить **на целевой версии `cloudflared`**, что конфигурация Tunnel действительно поддерживает Unix-origin и ожидаемый формат адреса. Плановое значение вида `unix:/ABSOLUTE/HOST/PATH/ingress.sock` не является доказательством совместимости установленного клиента.
3. Установить фактического пользователя systemd-сервиса `cloudflared`, UID/GID процесса Nginx в утверждённом web image, права и группу каталога на host. Значения из Mac/Docker-тестов не переносить на production.
4. Подготовить отдельный host-каталог под bind mount **до старта** нового web. Назначить владельца — фактический UID Nginx, группу — ограниченную группу с доступом `cloudflared`, режим `0750`. Посторонних пользователей в группе быть не должно. Не полагаться на автоматическое создание каталога Compose с правами по умолчанию.
5. Подтвердить, что новый Unix-вход доступен от `cloudflared` и недоступен постороннему локальному пользователю. Проверить состояние прав ещё раз после старта и после перезапуска контейнера: mount и инициализация способны изменить фактические владельца/группу.
6. Проверить готовность отката **обоих** компонентов: прежний web image и прежний TCP-origin Tunnel. Изменять только Tunnel или только web запрещено.

Любая неуспешная проверка — основание остановить переключение до изменения маршрута. Секреты и конфигурацию Tunnel не переносить в Git или тестовые логи.

## 4. Согласованный порядок cutover

Во время утверждённого окна: подтвердить health старого runtime; подготовить каталог и новый web; убедиться в работоспособности нового Unix origin **до смены публичного маршрута**; согласованно переключить Tunnel с TCP на Unix; проверить внешний Mini App HTTPS, `/healthz`, `/api/health/live`, `/api/health/ready`, реальную авторизацию, нормализацию IP и схемы, распределение разных клиентов по rate-limit buckets, webhook и Telegram smoke. Проконтролировать логи, рестарты, права каталога и недоступность Unix-входа постороннему пользователю.

**Запрещено:** развернуть новый web и оставить прежний `http://localhost:8080` как production origin. В таком сочетании клиенты Tunnel будут разделять адрес локального источника и общий rate-limit bucket.

При неуспешной приёмке вернуть **и** прежний web image, **и** прежний Tunnel TCP origin в согласованном порядке. Возврат одного маршрута при новом web не восстанавливает прежнюю модель работы. После отката повторно проверить внешний доступ и сохранить причины отказа; не объявлять CP-07 закрытым.

## 5. Доказательства, необходимые для закрытия

Нужны фактические значения production UID/GID, владелец/режим host-каталога, подтверждение доступности только разрешённому пользователю, проверка поведения двух разных внешних клиентов, рабочий внешний Telegram/Mini App сценарий, сведения о release provenance, время переключения, успешный health и проверенный rollback path. Одного `nginx -t`, локального `curl` или исходной конфигурации недостаточно.

## 6. Датированные локальные результаты, 19.09.2026

Сборка web Docker image и `nginx -t` прошли. В изолированном Docker-тесте TCP с десятью запросами и подменяемым `CF-Connecting-IP` вернул шесть `200` и четыре `429`: подмена не обошла лимит; backend видел непосредственный IP и схему `http`. Unix-вход для первого клиента также дал шесть `200` и четыре `429`, backend получил доверенный IP и `https`; второй клиент получил отдельный лимит и `200`.

Первоначальная проверка разрешений выявила проблему: при доступном каталоге сокет `0666` был доступен постороннему пользователю — **FAIL**. После настройки каталога `0750` (локально владелец `101`, тестовая группа `201`) пользователь `65534:65534` получил отказ, а `65533:201` — доступ. Во время одной инициализации Docker поменял группу каталога с `201` на `101`; повторная установка прав после старта восстановила требуемое поведение. Это объясняет необходимость проверки прав и на host, и после рестарта.

Все перечисленные результаты относятся **только к MacBook/Docker**. Пользователь `cloudflared`, права host bind mount, установленная версия Tunnel и реальная production-трасса на эту дату не проверялись. До их приёмки CP-07 остаётся `OPEN`.


## 7. Дополнительные результаты, 21.09.2026

В рабочей ветке добавлены `compose.ingress-unix.yaml`, отдельный
Compose-контракт и writable `tmpfs` для каталога сокета в базовом Compose.
Unix override сохраняет `/tmp`, заменяет каталог сокета на явный bind mount,
запрещает автоматическое создание host-каталога и удаляет опубликованный
TCP-порт. Это **не развернуто в production**.

Локально прошли 3 Compose-теста, 7 release-тестов и проверка структуры
документации. Отдельный Nginx-контейнер с read-only root filesystem успешно
создал Unix-сокет; `nginx -t` и HTTP `/healthz` прошли.

При испытании macOS bind mount `chown` завершился с кодом 0, но фактические
UID/GID каталога остались `0:0`. Этот механизм нельзя использовать как
доказательство корректных прав production Linux.

На Docker-managed Linux volume до старта установлены `101:201` и `0750`.
После запуска Nginx группа стала `101`; владелец остался `101`.
После восстановления `101:201` разрешённый клиент `65533:201` получил HTTP
200 через Unix-сокет, посторонний `65534:65534` — `EACCES`.
Это подтверждает локальную модель доступа, **не права production-хоста**.

### Обязательная поправка к cutover

`compose.ingress-unix.yaml` убирает публикацию TCP-порта. При замене
работающего web до смены Tunnel старый TCP origin перестанет отвечать.
Параллельное blue/green-развёртывание не реализовано и не проверено.
Текущий вариант допускается только в отдельно утверждённое окно с
предусмотренным перерывом доступа и проверенным откатом обоих компонентов.

Перед переключением необходимо на целевом Linux-хосте подтвердить:
фактические UID/GID Nginx и cloudflared, группу и права bind-каталога
**до и после запуска web**, создание сокета, HTTP-доступ разрешённого
пользователя, отказ постороннему, поддержку Unix origin установленной
версией cloudflared и работоспособность обратного переключения.

До выполнения этих условий CP-07 остаётся OPEN.


## 8. Production result, 25.09.2026

Фактическая принятая схема отличается от первоначально планировавшегося варианта «Cloudflare Tunnel → Unix socket напрямую»:

- `app.spik-inventory.ru` — direct public ingress; host Nginx терминирует TLS и проксирует в `/var/lib/dc-inventory-ingress/ingress.sock`;
- production web не имеет host TCP bindings и состоит только в `app_net`;
- `cloudflared` не является входом для пользовательского Mini App;
- отдельный hostname `telegram-webhook.spik-inventory.ru` опубликован через Tunnel `dc-inventory-prod` только для пути `/api/telegram/webhook`;
- Tunnel origin: `https://localhost:443`;
- origin settings: `HTTP Host Header=app.spik-inventory.ru`, `Origin Server Name=app.spik-inventory.ru`, TLS certificate verification включена;
- Cloudflare Access на webhook не используется; unmatched Tunnel routes закрываются `http_status:404`;
- `cloudflared` работает отдельным системным пользователем; `/etc/cloudflared` имеет ограниченный групповой доступ, token-файл читается сервисом и не хранится в Git.

Production acceptance:


После восстановления Telegram Tunnel входящий webhook был переключён с `https://app.spik-inventory.ru/api/telegram/webhook` на `https://telegram-webhook.spik-inventory.ru/api/telegram/webhook` с `drop_pending_updates=false`. Накопившаяся очередь уменьшилась с 9 до 0; updates `472023532..472023540` были приняты и обработаны, новые `sendPhoto`/`deleteMessage` завершились `SENT`, `last_error` после переключения отсутствовал. Реальный Telegram/Mini App smoke подтверждён в CP-17.

### Эксплуатационное правило

Не возвращать `app.spik-inventory.ru` за Tunnel без отдельного архитектурного решения. Текущая граница намеренно разделяет:

1. пользовательский Mini App/browser traffic — direct ingress;
2. Telegram inbound webhook — dedicated Cloudflare Tunnel hostname;
3. Telegram outbound delivery — Cloudflare Worker Gateway.

Изменение любого из этих путей требует отдельной проверки health, webhook secret, TLS/SNI, rollback и real Telegram smoke.
